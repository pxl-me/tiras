ТЗ

Необхідно реалізувати клієнт-серверну систему моніторингу сигналу апаратного пристрою (емулятор осцилографа), яка забезпечує потокову передачу даних у реальному часі, аналіз сигналу на сервері, збереження аномалій у базу даних та можливість керування типом сигналу з клієнтського застосунку.
Система повинна складатися з трьох частин: WPF-клієнта, серверної частини на ASP.NET Core Web API (.NET 8) та консольного емулятора пристрою.


1. WPF частина
Клієнтська частина повинна бути реалізована на WPF (.NET 8) із використанням MVVM та Dependency Injection. Бізнес-логіка не повинна розміщуватися у CodeBehind. Необхідно забезпечити чітке розділення на UI, application-логіку та інфраструктурний шар. Клієнт повинен підтримувати авторизацію, підключення до SignalR та відображення сигналу в реальному часі без фризів інтерфейсу. Для візуалізації дозволяється використання сторонніх бібліотек. Має бути можливість змінювати тип сигналу з інтерфейсу та відображати статус з’єднання і наявність шуму.

2. Емулятор осцилографа (Консольний додаток)
Емулятор має генерувати сигнал та передавати його на сервер у вигляді UDP-пакетів. Один пакет повинен містити 100 семплів типу float. Формат пакета передбачає заголовок із типом сигналу (enum: Sine, Square, Sawtooth), часовою міткою (long) та кількістю семплів (int), після чого передається масив значень сигналу. Передача відбувається в little-endian форматі. Емулятор також повинен мати можливість отримувати команди від сервера через SignalR. Через консольні команди має підтримуватися додавання шуму (випадкове відхилення ±10%), повне обривання сигналу (усі значення = 0) та відновлення нормальної роботи. Також має бути можливість змінювати тип сигналу під час виконання.

3. .NET Web API
Серверна частина повинна приймати UDP-потік, десеріалізувати пакети та виконувати базовий аналіз сигналу. Для кожного типу сигналу потрібно реалізувати еталонну математичну модель (sinus, square як sign(sin), sawtooth як лінійна функція в межах періоду) та порівнювати отримані семпли з еталонними значеннями. Метрикою відхилення є Mean Absolute Error. Якщо середня абсолютна похибка перевищує 0.15, сигнал вважається аномальним. У такому випадку сервер повинен зберегти запис у базу даних із зазначенням часової мітки, типу сигналу, величини відхилення та сирих даних (у вигляді JSON або bytea).
Сервер також відповідає за передачу потоку даних до клієнта. Для цього необхідно використати SignalR зі streaming-передачею (IAsyncEnumerable або Channel). Передаватися мають масив семплів, тип сигналу та ознака наявності аномалії. Доступ до SignalR-хабу повинен бути дозволений лише авторизованим користувачам.
Авторизація реалізовується за допомогою ASP.NET Core Identity із видачею JWT-токенів. Необхідно реалізувати реєстрацію, логін та захист API і SignalR-хабу через JWT. Коректне налаштування CORS є обов’язковим.

Архітектурно рішення має демонструвати розуміння розділення відповідальностей (Domain / Application / Infrastructure / Presentation). Бізнес-логіка не повинна розміщуватися у контролерах або UI-шарі. Бажано реалізувати логування та базові unit-тести для модуля аналізу сигналу.
